# חדר מוצר AIDD – סוכנים לצד האפיון וה‑Product

חדר סוכנים שמלווה דרישה עסקית מהרגע שהיא נכנסת ועד שהיא הופכת למסמך אפיון מוכן לפיתוח, יחד עם תמחור ולו"ז.
הפלט של החדר הוא הקלט של סוכני הפיתוח ב‑AIDD.

> **עיקרון מנחה:** הסוכנים מכינים, בודקים ומנסחים. **בני אדם מאשרים.** בכל שער (Gate) מסומן מי האדם שחותם.

### למה הסדר שונה מהרשימה המקורית?
ברשימה המקורית הלו"ז והתמחור באים מוקדם, אבל אי אפשר לתמחר ולתזמן ברצינות לפני שיודעים מה בונים.
לכן:
- **התמחור והלו"ז באים אחרי האפיון**, והם מבוססים על פירוק המשימות שבמסמך הפיתוח.
- **מוקדם בתהליך** המגבש נותן רק **הערכת גודל גסה** (S/M/L/XL). זה מספיק להחלטה אם להמשיך.
- **שירותים/דאטה ו‑UI/UX רצים במקביל**. שניהם צריכים רק את הדרישה המגובשת, והמאפיין צריך את שניהם.

## 3. מבנה התיקייה של כל דרישה

כל דרישה מקבלת תיקייה משלה. הסוכנים מתקשרים **רק דרך הקבצים** ולא דרך שיחה, וכך יש עקיבות מלאה.

```
requests/REQ-123-short-name/
├── 00-request.md          # הדרישה כפי שהתקבלה (נכתבת על ידי אדם)
├── 01-shaping.md          # מגבש דרישה
├── 02-services-data.md    # שירותים, תהליכים, דאטה
├── 03-ux.md               # UI/UX
├── 04-dev-spec.md         # מאפיין ← הקלט לפיתוח
├── 05-estimate.md         # מתמחר
├── 06-schedule.md         # לו"ז
├── status.md              # מנהל החדר: שלב נוכחי, שערים ושאלות פתוחות
└── decisions.md           # יומן החלטות של בני האדם (מי, מתי ומה אושר)
```

תבניות לכל קובץ נמצאות ב‑`templates/`.

## 4. איך מפעילים

1. מעתיקים את `.claude/agents/` לריפו של צוות המוצר, או לתיקייה `~/.claude/agents/` לשימוש אישי.
2. יוצרים תיקיית דרישה חדשה ושמים בה `00-request.md` לפי התבנית.
3. ב‑Claude Code מבקשים:
   ```
   השתמש ב-room-lead כדי לקדם את requests/REQ-123-short-name
   ```
   מנהל החדר יפעיל את הסוכן המתאים לשלב, יעדכן את `status.md` ויעצור בכל שער לאישור אנושי.
4. אפשר גם להפעיל סוכן בודד ישירות, למשל: `השתמש ב-estimator על REQ-123`.

| סוכן | מקור ידע שכדאי לחבר | איך מחברים |
|------|----------------------|------------|

| לו"ז | קיבולת צוותים, חופשות, ספרינטים, תלויות בין צוותים | `context/capacity.md` / MCP ליומן ול‑Jira |

## 6. תוכנית הטמעה מוצעת (Long Run)

| שלב | משך | מה עושים | מדד הצלחה |
|-----|-----|----------|-----------|
| **א. פיילוט צללים** | 3–4 שבועות | החדר רץ במקביל לאנליסטים על 3–5 דרישות אמיתיות. משווים את התוצרים, ושום דבר לא יוצא לפיתוח מהחדר | האנליסטים מסמנים בכמה מהתוצרים היו משתמשים |
| **ב. טיוטה ראשונה** | 1–2 חודשים | החדר מייצר טיוטה, והאנליסט עורך ומאשר. מתחילים עם המגבש והמאפיין, שבהם הרווח הגדול ביותר | קיצור זמן מדרישה למסמך פיתוח |
| **ג. חדר מלא** | לאחר מכן | כל השלבים פעילים, ואנשי המוצר משמשים מאשרים ובעלי שערים | פחות חזרות מהפיתוח בגלל אפיון חסר; פער ההערכה מול הביצוע |

**מדדים למעקב:** זמן מחזור מדרישה ל‑Ready, מספר שאלות הבהרה שחוזרות מהפיתוח, דיוק הערכות (±%) ושיעור דרישות שנדחו מוקדם (זה דבר טוב).

## 7. התפקיד של האנליסטים וה‑PO אחרי המעבר

התפקידים לא נעלמים, הם משתנים:
- **אנליסט מערכות** הופך מכותב מסמכים ל**מבקר ובעלים של איכות האפיון**. הוא מתחזק את קטלוג השירותים ואת הקונטקסט שהסוכנים משתמשים בו.
- **PO** הופך לבעלים של השערים ושל ההחלטות: עדיפות, היקף ופשרות. הוא מקבל טיוטות מוכנות במקום לכתוב מאפס.
- **מומלץ:** לשתף אותם בכתיבת הפרומפטים של הסוכנים, כי הידע שלהם הוא מה שהופך את הסוכנים לטובים. זה גם מפחית התנגדות.
